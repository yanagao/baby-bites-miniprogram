**家庭共享当前实现**：从「我的 → 我的家庭」创建家庭并邀请爸爸、妈妈、爷爷奶奶等家人。首版一个家庭对应一个宝宝，每个微信账号同时加入一个家庭；共享宝宝称呼、生日、过敏食物、菜谱、照片、收藏和用餐记录。创建时使用创建者已同步的数据；其他人确认加入后切换到家庭数据，各自原来的个人记录保留，不自动混入家庭。新用餐记录显示记录人的称谓，历史记录不猜测记录人。管理员可以邀请、移除和转让权限，称谓与管理权限分开。推荐过滤开关属于每位成员在本机的个人偏好，不随家庭记录同步。

家庭邀请由管理员生成，24 小时内单次使用；重新邀请使旧邀请失效。加入前先展示家庭信息并确认，之后才获得家庭数据；这是加入家庭确认，不是菜谱分享预览。退出前须完成同步；管理员有其他家人时须先转让，最后一人可确认解散。家人都能修改共同菜谱和宝宝资料。菜谱首次自动公开由添加者自己的同步触发，其他家人可转发已有链接、共同更新已公开做法并保留原作者；不替另一成员创建公开身份。家庭生日和过敏记录不进入公开菜谱。创建家庭后，添加者自己的同步会把其原个人公开菜谱关联到当前家庭，保留作者和原链接；其他家人不能代迁，离开家庭不会自动改回个人，也不会从另一个家庭迁入。

家庭照片由服务端另存为家庭文件，经成员校验后发放短期地址；不开放个人照片目录。缓存、异步请求和备份按账号、家庭及本次成员资格隔离，切换家庭清空旧草稿，离开后重新加入不复用旧成员的待上传缓存。修改先保存在本机，联网后同步给家人；多人修改按条目版本合并，没有持续实时推送。家庭页面和照片读取合并请求，照片每批最多 20 张。

上线须创建 [家庭集合与索引](cloudfunctions/babyBitesSync/family-database.json) 和 [反馈集合与索引](cloudfunctions/babyBitesSocial/feedback-database.json)，部署配套的 `babyBitesSync`、`babyBitesSocial`，再上传新版客户端。旧客户端加入家庭后会收到更新提示，不能覆盖家庭数据。部署证据和多账号真机验收另记，不以本地源码或单元测试代替。

## 已实现

- **菜谱真实反馈**：「我的」中的“收到的反馈”入口已移除，现有反馈数据与后端接口保留。保存者成功收进自己的食谱并完成云同步后，服务端验证副本来源，再写入匿名保存回执；同一人保存同一道菜只记一次。失败回执按账号保留并在后续同步重试，不阻塞本地保存，也不补造历史保存记录。
- **我做过这道菜**：公开菜谱和保存副本保留跟做入口，只需一张成品照与 1–120 字反馈，不要求完善主页资料。提交前说明公开昵称、成品照和留言的展示范围；审核通过后展示在菜谱反馈中。本人不能给自己的菜谱制造反馈，内置及下架菜谱不展示反馈；自己发出的跟做可以删除。成功后可选择整理做法，保存副本仍保留原作者来源，不另发重复菜谱。交互参考 [Cookpad Cooksnap](https://cookpad.com/us/cooksnap_intro)。
- **反馈读取与重试**：菜谱反馈沿用 30 秒缓存与并发读取合并，不新增轮询；需要时手动刷新。跟做请求有稳定标识避免重试重复发布，删除保留墓碑阻止旧请求恢复；账号切换清空展示和草稿。照片按需压缩为最长边不超过 750px、1 MB 内的 JPG/PNG；原菜谱照片和私人用餐记录不被自动用作跟做反馈。

反馈功能的云端配置见 [反馈集合与索引](cloudfunctions/babyBitesSocial/feedback-database.json)，新集合需设置客户端不可读写并创建三个复合索引；`security.imgSecCheck` 权限需随云函数部署。当前源码不代表这些配置已经在线生效，跟做审核、双账号保存回执和真机图片提交仍需上线验收。

- **宝宝过敏食物**：在「我的 → 宝宝过敏食物」记录常用或自定义食物，保存后生效；最多 50 项，每项 1–40 字。未加入家庭时记录仅自己可见，加入后家庭共享，随数据同步和备份保留，不进入公开主页、菜谱或分享卡。“推荐时跳过过敏食材”开关默认关闭、立即生效，只使用已保存的记录；开启后首页推荐、随机选餐、按食材找菜、发现和关注动态跳过匹配食材。开关仅保存在本机，按账号、个人/家庭范围和本次成员资格隔离，不同步给其他设备或家人、不写入备份；新成员资格默认关闭。关闭开关不删除过敏记录，自己的菜谱、收藏、历史记录及详情命中提示仍保留。

过敏匹配基于菜谱已填写的食材名称、常见别名及明确的食品名称，如鸡蛋/蛋黄/蛋清、大豆/豆腐、牛奶/奶酪；自定义项按名称匹配。这不是完整的复合配料数据库，不把未匹配标记成「无过敏原」或「安全」。包装配料仍需核对，参见 [NHS 儿童食物过敏与配料标签说明](https://www.nhs.uk/baby/weaning-and-feeding/food-allergies-in-babies-and-young-children/)。

**餐单上线顺序**：先部署本次 `babyBitesSocial`，再部署 `babyBitesSync`，最后发布新客户端，使读取端先兼容用餐记录删除历史中的创建时间。餐单存于现有个人/家庭快照与备份，不增加集合或索引，不进入公开菜谱；旧客户端在餐单启用后被服务端阻止覆盖新字段。新快照可选 `mealPlans` / `deleted.mealPlans` 配对保存，最多 3000 个安排、30000 个餐单删除标记；空数组也保留新字段保护。源码与本地测试不代表线上已部署。

备份合并通过稳定记录 ID 识别原餐次，支持删除后换菜重建、再修改用餐日期或餐次的记录。已移动的记录作为独立用餐历史合并，原餐单后来换菜或移除也不会丢失该记录；未移动的重建记录与对应餐单一起检查冲突，较新本地餐单及普通记录 ID 碰撞的保护保留。

同一餐删除后重新完成会复用稳定 ID，但通过删除时间与创建时间区分新旧记录。家人重新点击「已做」后，由云端标记实际操作成员，不继承旧记录人；修改反馈和恢复同一次历史记录保留可验证的原署名。备份导入不会把无法核实的记录署成导入者；旧记录试图覆盖云端的新一代记录时保留冲突保护。

**请求与刷新（2026-11-02）**：发现、关注和主页在 30 秒内复用有效内容，返回页面保留已加载分页；同一查询的并发请求会合并。社交数据只在当前进程缓存（最多 32 项、2 MiB），按账号、查询条件和分页隔离，手动刷新跳过缓存。保存资料、关注、菜谱自动公开/更新/删除及真实同步版本变化会使缓存失效；账号切换或身份失效立即清理。分享菜谱详情每次打开仍请求服务端确认菜谱仍存在、可共享且不属于内置来源。作者关注状态使用轻量 `profileSummary`，不再下载完整主页菜谱列表。

本地与公开菜谱详情仅在本次分享匹配微信报告的原生页面切换、且身份和数据版本未变时复用已确认的信息。取消分享而没有切换页面时，待匹配标记会自动清除；普通退出、页面导航或无法确认切后台原因时重新校验，避免原作者改名或删除后仍分享旧标题或失效链接。旧基础库未提供切后台原因时也采用重新校验；内置菜谱继续直接读取原版，无需请求公开接口。

账号缓存使用本机 `__sync.snapshotSchemaVersion` 标记完整快照的解析版本，与数据原子保存，不进入云端快照或备份。旧缓存即使 revision 相同，也须先重新下载，以恢复旧客户端可能丢弃的过敏字段；下载、校验或保存失败不会补写标记。恢复成功后继续复用同版本缓存；旧客户端再次写入缓存会丢弃未知元数据，重新升级时仍会恢复完整快照。MR #3 对应升级路径修复已通过 1048 项测试与原生编译、包体预检。

**此前请求性能优化验收（本次策略调整前）**：1038 项测试通过，17 页、215 个 JS/WXS 脚本及原生编译、包体预检通过；`babyBitesSocial` 已部署并确认 Active，8 个 JS/JSON 运行文件与本地一致。模拟器检查发现列表、公开详情及返回、我的资料和关系均正常；未写入测试业务数据。请求数量和并发收益由自动测试验证，尚无真机网络耗时对比，客户端未提审发布，见[请求性能核验记录](../output/request-performance/verification.json)。

“推荐时跳过过敏食材”是另一项本机偏好，默认关闭，存储键包含账号、scope 和 membershipId。切换开关不修改共享过敏记录、不触发数据快照上传，也不进入导出备份；其他家人、其他设备和新的成员资格分别从关闭状态开始。开启后只按已保存的过敏记录筛选，未保存草稿不会改变推荐。

同一微信账号在同一正式 AppID、同一云环境下，可以同步宝宝称呼、菜谱、照片、收藏及用餐记录。未加入家庭的不同微信账号分别保存；确认加入同一家庭后共同记录同一个宝宝。不同 AppID、其他云环境及网页版不会自动合并，需要由用户导入备份迁移。同步不需要读取微信昵称、头像或手机号。

修改先保存到本机，再自动同步到当前个人或家庭；进入前台、联网恢复和后续修改会触发同步，也可在设置中重试。快照提交成功后，`syncPublications` 分批首次公开或更新自有非内置菜谱，并移除已删除、内置来源或重复收藏副本的公开记录。策略 v3 会对仍存在的历史自有菜谱重新对账；不会公开宝宝资料、心得或日志，也不会恢复权威快照已删除的菜谱。家庭首次公开使用添加者身份，其他成员只更新既有公开版本。分享不需要预览；公开处理暂时失败时本机保存仍有效，保留待同步状态并重试。换设备前确认“已同步”，首次恢复和照片下载需要网络。

旧版本数据键 `baby-bites-v1` 继续保留。首次成功识别微信账号时，将未绑定的旧数据合并到该账号缓存，并记录迁移归属，防止再次合并给另一个账号。账号缓存使用 `baby-bites-account-<owner>`，当前缓存标识使用 `baby-bites-active-owner`；`owner` 是服务端从微信可信身份计算出的哈希，不由客户端自报。没有网络时保留最后一次确认账号的本机修改，未能确认的新账号不会上传旧账号数据。切换 AppID 后旧照片路径可能失效，迁移前须先导出含照片的备份。

多设备同步按条目 ID 合并，较新的 `updatedAt` 优先；同一条目的同时编辑不会逐字段拼接。明确导入本机已知删除的条目会作为恢复操作保留；相同版本的备份可修复已失效的本机照片，不替换有效照片或较新内容。删除先原子保存本机删除墓碑，再提交账号快照；服务端对账时据此移除已不在快照中的共享菜谱，离线或暂时失败不会回滚本机删除，会保留待同步状态。删除记录也避免另一设备的旧缓存把已删内容恢复；删除菜谱后，其对应的用餐记录也不会重新出现。云端以版本号事务提交，有冲突时先读取新版本、重新合并再提交，不直接覆盖其他设备的新内容。同步期间继续编辑的本机变化保留在下一次同步队列里。

菜谱更新、用餐记录新增及编辑都先校验后提交；存储失败时不更新内存。读取到损坏内容时保留原存储，普通编辑会被阻止，需导入有效备份恢复。记录编辑保留 `id` 和 `createdAt`，增加可选 `updatedAt`；旧备份缺失该字段时按 0 处理，合并时保留同一条记录较新的修改。

未同步照片使用微信持久文件路径；个人同步成功后使用属于当前账号的云端照片，家庭同步使用服务端维护的家庭照片。导出时将本机或云端照片转换为嵌入图片的 JSON，导入时重新保存到当前设备。新选菜谱照片先在本机自动压缩：源图最多 20 MiB，长边不超过 1600px，以 512 KiB 为目标逐级调整画质和尺寸，最终不得超过 2 MiB；已足够小的图片直接复用。历史未上传照片和备份导入的本地照片在同步上传前同样处理，已有云端照片不重复下载压缩。压缩失败保留原图，压缩临时文件在替换、放弃或成功持久化/上传后清理。备份导入的单张图片仍最多 2 MB，备份文件最多 20 MB，云端数据快照最多 5 MiB（照片独立存储，不嵌入快照）。

导出分两步：先生成备份文件，再点击「分享备份文件」（手机）或「保存到电脑」（桌面微信）。文件分享必须由新的点击直接触发，不能在照片异步读写完成后自动调用。取消、失败或离开待确认页面会清理临时备份；正在分享的文件等系统回调后再清理。导出不修改原有菜谱、照片和用餐记录。

开发者工具 2.02.2608080 / 基础库 3.7.12 实测可生成含照片的备份，但不支持 `shareFileMessage` 文件分享调试；需在手机微信完成分享验收，或手动使用「其他备份方式 → 复制备份内容」。

## TDesign 与重新构建

修改组件引用或重新生成依赖时，在本目录运行（需要 Node.js 和 npm）：

```sh
npm ci
npm run build:components
npm run validate
```

官方「工具 → 构建 npm」会复制整个 `miniprogram_dist`。本项目基于同一发布产物按需复制，并设置 `lazyCodeLoading: "requiredComponents"`，只注入当前页面声明的组件。不要额外导入 TDesign 总入口；组件在所需页面或组件 JSON 中单独声明。若官方 npm 构建覆盖了产物，再运行 `npm run build:components` 恢复按需版本。`npm run check:package`（也包含在 `npm run validate` 中）按打包配置检查主包源文件体积、分包和单个媒体资源的大小；它是保守预检，最终编译体积以开发者工具预览/代码质量扫描为准。闲置字体和本地 `output/` 文件不打包。

## 交互依据

交互继续参考 [Apple HIG](https://developer.apple.com/design/human-interface-guidelines)，通过小程序和 TDesign 的公开能力实现，不复制 iOS 系统控件外观。

- [Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)：四个 Tab 稳定对应「首页 / 发现 / 记录 / 我的」，中央添加是独立操作，选中状态来自真实路由。
- [Writing](https://developer.apple.com/design/human-interface-guidelines/writing) 与 [Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)：操作写明结果；家长收藏、宝宝喜好、新增用餐和编辑历史分别表达。
- [Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data) 与 [Pickers](https://developer.apple.com/design/human-interface-guidelines/pickers)：普通新增默认今天，从记录日历新增沿用选中日期；喜好不预选，食量选填，错误贴近字段。
- [Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback)：选中食材同时有勾与底色，并提供可移除标签；收藏使用图标和文字；保存失败保留输入，防止重复提交。
- [Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts) 与 [Modality](https://developer.apple.com/design/human-interface-guidelines/modality)：丢弃修改、删除和合并导入需要确认，删除菜谱说明关联记录数量。
- [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)：导航保留文字，反馈不只依赖颜色，图标按钮提供中文名称；字号及读屏效果仍需真机检查。

此前调研参考 [Solid Starts](https://solidstarts.com/articles/solid-starts-app-new-first-100-foods/)、[Huckleberry Solids](https://huckleberrycare.com/product/solids)、[BLW Meals](https://blwmeals.com/)、[Paprika iOS 手册](https://www.paprikaapp.com/help/iphone/)、[SuperCook 开发者说明](https://apps.apple.com/us/app/supercook-recipe-by-ingredient/id1477747816) 与 [下厨房帮助中心](https://www.xiachufang.com/faq/)，用于区分菜谱、食材检索、收藏和每次用餐体验。这些是文档调研，不表示实测过各产品当前版本；随机选菜来自本项目自己的需求。

统一术语：宝宝反馈使用「不太喜欢 / 还不错 / 很喜欢」；家长偏好使用「收藏 / 已收藏」；用餐数据使用「用餐记录 / 用餐日期 / 食量」，食量可选「吃了一点 / 吃了约一半 / 吃了大部分 / 全部吃完」。

## 字体、图标与运行边界

TDesign 图标使用官方 0.4.5 字体原始字节，Base64 数据保存在 `recipe-media/fonts/tdesign-icons-0.4.5.js`。启动时通过 `require.async` 获取资源分包中的字体，再调用 `wx.loadFontFace`；分包缓存后可离线加载。微信 API 定义从基础库 3.7.9 开始支持 Data URL；低版本、分包不可用或本地字体加载失败时回退官方 HTTPS 字体。每阶段最多等待 10 秒，并发请求合并、成功缓存，失败后可重试；字体准备不阻塞页面操作。原始图标字形和字体字节未修改，颜色与尺寸通过公开 API 设置。依据见 [微信官方 API 类型定义](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.api.d.ts) 和 `assets/fonts/NOTICE.txt`。

当前标题、正文及兼容保留的 `.brush` 类均采用系统无衬线字体。历史 PocketBrush 字体源码已移到工作区 `output/cute-assets-original/pocket-brush.js` 存档，不再加载或打包；字符、来源与重建说明见 `assets/fonts/README.md`。口袋 Logo 与全部食材插画保持原画面；食材图集仅重新压缩 PNG 数据流，像素、尺寸、透明度和颜色元信息均不变，记录见 `assets/cute/ASSETS.md`。

顶部使用 TDesign Navbar 和官方 `placeholder` 处理状态栏与微信胶囊；底部 TDesign TabBar 在四个 Tab 页正文末尾渲染，其 `placeholder` 参与页面布局。原生自定义导航宿主仅保留空壳，避免重复导航和占位失效。

未保存提醒仅在实际修改后启用。两个编辑页的返回及取消按钮使用放弃确认逻辑，微信 `enableAlertBeforeUnload` 作为系统返回的补充。微信文档不保证拦截侧滑返回，因此不声称所有退出方式都能恢复草稿。
